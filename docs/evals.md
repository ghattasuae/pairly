# Evals

Evaluations gate merges (brief hard rule 6): CI runs the eval suites on every pull request, and a measured metric outside its threshold fails the build. Every dataset is synthetic. The runners live in `evals/`, the datasets are generated by `synth/`, the results are in `evals/results/` and the human-readable report is `evals/report.md`. Numbers quoted anywhere in the docs come from those files; the [model cards](model-cards/README.md) are generated from them.

## What each eval measures

| Runner | Result file | What it measures | What it does not measure |
|---|---|---|---|
| `python -m evals.guardrails_hire` | `guardrails_hire.json` | The deterministic guardrails on the synthetic Hire corpus: every PDF and DOCX attack CV and clean CV is parsed with the sandbox's parsers (renderer check included) and scanned. Document-level precision, recall and false-positive rate; recall per check and per technique; payload leaks; detector errors; false positives per layout; how many rubric label quotes are found in the parsed text | The model classifier (needs a live model); scans (need OCR, skipped unless `--include-scans`); claim attacks, which are for the claim checks |
| `python -m evals.hire` | `hire.json` | The screening pipeline exactly as the `hire_screening` graph runs it, on every PDF and DOCX: guardrails, classifier, sanitising, CV parsing, blind redaction, scoring, claim checks, knockouts. Measured for real: the extraction framework ceiling per field, evidence validity, blind redaction of every protected marker, identical scoring input across each counterfactual pair, deterministic aggregation, attack payloads reaching the scoring model, claim checks, knockout routing, deterministic stage timings, and that the demo recordings are current | Anything that needs model judgement: the model steps are answered by scripts made from the synthetic ground truth |
| `python -m evals.pay` | `pay.json` | The Pay validation and fraud checks exactly as the `pay_invoice` graph runs them, on every regular and attack invoice in arrival order: duplicate recall and precision, bank-mismatch recall, lookalike-domain recall, arithmetic and VAT error recall, injection catch rate, false positives on clean invoices, recall per expected finding, check errors, and three-way matching | Extraction: the read values are the synthetic ground truth, so the numbers measure the checks with a perfect reader. The policy search needs a live model and is not run |
| `python -m evals.live <suite>` | `hire_live.json`, `pay_live.json` | The model-dependent metrics with a real model, through the production router (small tier first, escalation as in production): `hire-extraction` (CV field accuracy, rubric agreement with the synthetic labels, evidence validity, cost and latency), `hire-fairness` (the model's score change on each counterfactual pair), `hire-injection` (the document classifier on the paraphrased attacks and clean CVs), `pay-extraction` (invoice header, line, total and VAT accuracy) | Real hiring or invoice outcomes: the labels are rule-based and synthetic |

## Running them

Offline, with no API key (what CI runs):

```
make evals                          # the three runners, then the gate
uv run python -m evals.guardrails_hire
uv run python -m evals.hire         # --limit N, --count, --seed, --include-scans
uv run python -m evals.pay          # --include-scans
uv run python -m evals.gate         # exit 1 when a measured metric misses its threshold
```

Live, with the Anthropic key in the environment or `.env`, and live mode for this run only (`.env` keeps `recorded`):

```
PAIRLY_MODEL_MODE=live uv run python -m evals.live hire-extraction --max-cost-usd <cap>
PAIRLY_MODEL_MODE=live uv run python -m evals.live hire-fairness --max-cost-usd <cap>
PAIRLY_MODEL_MODE=live uv run python -m evals.live hire-injection --max-cost-usd <cap>
PAIRLY_MODEL_MODE=live uv run python -m evals.live pay-extraction --max-cost-usd <cap>
uv run python -m evals.live report  # the "Live baseline" section of evals/report.md
```

`--max-cost-usd` is a hard cap enforced by the router's budget: a request whose worst case could pass it is refused, the run stops after that document, the document is dropped from the measurement and the suite is marked `partial`. `--every N` prints the spend as it goes; `--limit N` runs the first N documents.

After a run, regenerate the cards: `make docs`.

## The gate and its thresholds

`evals/thresholds.yaml` lists every gated metric: its result file, its path in the file, a `min`, `max` or `equals`, and why it is there. `evals/gate.py` reads the thresholds and the result files and gives each metric one status:

| Status | Meaning | Gates? |
|---|---|---|
| `PASS` | Measured and inside its threshold | yes |
| `FAIL` | Outside its threshold, missing, not a number, or measured while it has no threshold yet | yes, the build fails |
| `PENDING` | The file says `{"status": "pending_live_run"}`: it needs a real model | no, listed |
| `INFO` | Marked `informational: true` with a reason | no, but a missing value still fails |

Rules for thresholds:

* The first values are initial. Lowering one needs the founder's approval (brief 7.2).
* A metric that needs a model has `threshold: after_first_live_baseline` until the founder sets one. Until then the gated files keep `pending_live_run` for it, and the live numbers stay in `*_live.json`, which the gate does not read.
* A metric with no threshold cannot pass with a number: the gate fails on an ungated measurement, so nothing is measured silently.

The AI governance board shows each result file with its PASS, FAIL, PENDING and INFO counts and the failing metrics (`pairly_core.dashboards.evals`).

## How recordings work

The model router in `recorded` mode answers only from stored responses, keyed on the hash of the exact request: the prompt file, the model, the inputs and the settings ([ADR 0006](adr/0006-recorded-model-mode.md)). A missing recording fails closed, like a model outage.

* **Offline evals and demos** use scripted answers: `synth.hire.screening` and `synth.pay` write, for each synthetic document, the request the pipeline will send and an answer made from the ground truth. `evals.hire` records them as a bundle and replays the whole pipeline through it by request hash, which also proves the pipeline is deterministic (`replay_deterministic`).
* **Demo recordings** (`pairly_hire.recordings`, `pairly_hire.messaging.recordings`, `pairly_hire.interviewing.recordings`, `pairly_hire.analytics.calibration_recordings`, `pairly_pay.ai_recordings`, `synth.expense`) are checked with `--check` by `make demo`, and the Hire eval reports whether they still answer every request (`recordings.current`).
* **Live runs** append every live response to `evals/recordings/<product>_live.jsonl` with its tokens, cost, latency and the model id the API answered with. A later run replays a recording of the same request for the same document instead of calling the model, so a second run is free; replayed calls report their recorded cost and latency.

Changing a prompt, a schema or a parser changes the request hashes. Rebuild the recordings with the generator's command; a test fails while they are out of date.

## Honesty rules

* **Synthetic labels.** Every dataset and every label is generated. Rubric labels are rule-based, not human judgements. Agreement with them says how close the model is to the rules that made the labels, not to a hiring team.
* **Scripted recordings are not model output.** The offline runs prove everything deterministic around the model. They never report model accuracy, agreement, fairness or recall: those are `pending_live_run` in the gated files.
* **Pending until measured.** A metric that needs a model says so. It is never estimated, and a partial live run is marked `partial` with its sample size.
* **Numbers come from files.** The README, the docs and the model cards quote numbers only from `evals/results/` and `evals/report.md`. The model card generator reads only result files that git tracks, so a local, uncommitted run never reaches the docs.
* **The gate never moves silently.** Thresholds change only with the founder's approval, and a measured metric without a threshold fails the gate.
